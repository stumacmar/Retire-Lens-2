# Typography and motion for live numbers; technical feasibility and accessibility of a one-screen rotational instrument in a phone browser

Scope: evidence for (1) numeral typography and number motion that reads modern, minimal and trustworthy; (2) motion design systems worth copying, with concrete spring/duration values; (3) how to build and make accessible a touch dial/drum/radial control with a live-updating output on iOS Safari and Android Chrome, in React 19 + Tailwind v4, no backend. Reference device: three-year-old phone, 390 × 844 (375 × 667 must work). Sources were examined directly where the page could be fetched; several Apple HIG pages were read through their `.md` endpoints. Where a page would not render (Material 3 site) the figures were taken from the AndroidX source instead. Items I could not verify are in each Gaps section rather than stated as fact.

---

## 1. Display numerals: what makes a large currency figure feel precise yet warm?

### Takeaway
There is no peer-reviewed evidence that serif numerals are more or less legible than sans at display size on phones; the evidence that exists says the serif/sans choice alone is not the deciding factor, while size, weight, case and the specific typeface are. The practical rule from Apple's own clock and from type foundries is: use tabular (fixed-width) lining figures wherever a figure changes under the user's hand, accept the slightly looser "1", and use proportional figures only where the number is static. Apple's watch complications use SF Compact Rounded; a soft serif (Fraunces) or a condensed display serif (Instrument Serif) gives the "warm" quality the owner wants, but Instrument Serif is a two-style static display face with no documented tabular figures, so it must be tested with `font-variant-numeric: tabular-nums` before being chosen for the live headline.

### Cited Findings
- Apple's Human Interface Guidelines state: "SF Compact is the system font in watchOS, and apps can also use NY. In complications, watchOS uses SF Compact Rounded." The system also offers SF Pro, SF Compact and others "in rounded variants you can use to coordinate text with the appearance of soft or rounded UI elements, or to provide an alternative typographic voice." — [Apple HIG, Typography](https://developer.apple.com/design/human-interface-guidelines/typography)
- Apple's system fonts use "dynamic optical sizes, which merge discrete optical sizes (like Text and Display) and weights into a single, continuous design, letting the system interpolate each glyph or letterform to produce a structure that's precisely adapted to the point size." — [Apple HIG, Typography](https://developer.apple.com/design/human-interface-guidelines/typography)
- Apple's recommended text sizes on iOS: default 17 pt, minimum 11 pt; "If you use a custom font with a thin weight, aim for larger than the recommended sizes to increase legibility." — [Apple HIG, Typography](https://developer.apple.com/design/human-interface-guidelines/typography); same table repeated in [Apple HIG, Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- Apple's minimum contrast guidance (from WCAG AA): 4.5:1 for text up to 17 pt, 3:1 at 18 pt and above or for bold text; check both light and dark appearances. — [Apple HIG, Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- Analysis of the iOS lock-screen clock: proportional figures make the time "jump" when minutes change, with the narrow "1" the worst case; tabular figures stop the jump but a "1" in a fixed-width slot leaves gaps so that "12:11" "almost falls apart"; a serifed alternate "1" closes the gap but "totally changes the character of the typeface into something more technical". The author's practical rule: "Use tabular figures where values must not move, such as counters, tables, and price lists." San Francisco ships both proportional and tabular lining figures. — [Pimp my Type, "Improving the Typography of the iOS clock"](https://pimpmytype.com/ios-clock/)
- GNOME's GTK issue on Adwaita: a font defaulting to proportional figures "will cause numbers to jump when changing and not line up with figures above and below", which is why tabular figures were requested as the default for UI elements. — [GNOME GTK issue #41](https://gitlab.gnome.org/GNOME/gtk/issues/41)
- Foundry guidance: "proportional figures are appropriate when numerals are going to be read in text, and tabular figures are preferable when numerals will be read in columns." — [Fonts.com Fontology, Proportional vs Tabular figures](https://www.fonts.com/content/learning/fontology/level-3/numbers/proportional-vs-tabular-figures)
- Design-system guidance (Maersk): use monospaced/tabular numbers for "Numbers, where the values are changing dynamically, such as file sizes and time elapsing on videos." — [Maersk Design System, Monospaced numbers](https://designsystem.maersk.com/content/numbers/monospaced-numbers/)
- On the web the mechanism is `font-variant-numeric: tabular-nums;`, but "if the font doesn't have tabular figures, the property won't magically invent them." — [DEV Community, Tabular numbers in CSS](https://dev.to/alanwest/tabular-numbers-in-css-font-variant-numeric-vs-monospace-hacks-25cn)
- Fraunces is a "display, 'Old Style' soft-serif typeface inspired by early 20th-century typefaces" (Windsor, Souvenir, Cooper). Variable axes: opsz 9–144 (lower values give taller x-height, more open spacing and wider characters), wght 100–900, SOFT 0–100, WONK 0–1 (binary, auto-enabled when opsz > 18). Licence: SIL OFL 1.1. — [undercasetype/Fraunces on GitHub](https://github.com/undercasetype/Fraunces); axis details also in [arrowtype/Fraunces](https://github.com/arrowtype/Fraunces)
- Instrument Serif is "A condensed, display serif designed for the Instrument brand", designed by Rodrigo Fuenzalida with Jordan Egstad, two styles (Regular and Italic), intended for large sizes, SIL OFL 1.1. No OpenType figure features are documented. — [Instrument/instrument-serif on GitHub](https://github.com/Instrument/instrument-serif); [Fontsource, Instrument Serif](https://fontsource.org/fonts/instrument-serif/about)
- A Penn State display-legibility study found "the choice of serif versus sans-serif alone does not have an important effect on display legibility"; typeface selection changed reading distance and uppercase often read better than lowercase. Subjects used a monitor, not a phone. — [International Journal of Signage and Wayfinding](https://journals.shareok.org/ijsw/article/download/3/1/7)
- A 2020 *Ergonomics* study of at-a-glance legibility compared eight sans-serif typefaces and found the typeface "can affect legibility at-a-glance", but did not compare serifs. — [Ergonomics 2020](https://informahealthcare.com/doi/full/10.1080/00140139.2020.1714748)
- Richardson's 2022 Springer monograph reviews legibility of serif and sans-serif "when used with internet browsers, smartphones and other hand-held devices". — [Springer, The Legibility of Serif and Sans Serif Typefaces](https://link.springer.com/chapter/10.1007/978-3-030-90984-0_12)
- Apple on text with depth (visionOS, but relevant to any 3D drum carrying numerals): "In general, prefer 2D text. The more visual depth text characters have, the more difficult they can be to read." and "Keep text facing people as much as possible" (billboarding). — [Apple HIG, Typography](https://developer.apple.com/design/human-interface-guidelines/typography)
- NumberFlow's own examples set `font-variant-numeric: tabular-nums` and `line-height: 0.85` on the animated figure, and its mask defaults are `--number-flow-mask-height: .25em` and `--number-flow-mask-width: .5em`. — [NumberFlow docs](https://number-flow.barvian.me/)

### Inferences
- For the live headline (£ a month after tax), choose a face that has true tabular lining figures and an optical-size axis so the same family works at 64–80 px for the headline and 13–15 px for labels: Fraunces satisfies both the "serif numerals" preference and the variable-axis requirement (opsz 9–144) and is free. Instrument Serif is the more fashionable choice but, being a two-style static display face, it should only be used if a browser test shows its digits are already near-uniform in width or if the figure is rendered digit-by-digit in fixed-width cells (which is what a drum/odometer does anyway).
- The Pimp my Type trade-off suggests a hybrid for a currency figure: tabular figures while the value is moving under the finger, with the "1" gap accepted; the number stops moving when the finger lifts, so the gap is only visible for the duration of the gesture.
- "Precise yet warm" is achieved by weight and optical size rather than serifs per se: a high opsz instance (thin hairlines, tight spacing) at display size, medium rather than light weight for contrast on a dark atmospheric background (Apple's warning about thin custom fonts), and tabular figures so the number reads as an instrument reading rather than prose.
- Any numerals rendered on a rotating 3D surface should be billboarded (flat to the viewer) or rendered as 2D overlays; Apple's own guidance is that text with depth is harder to read.

### Gaps
- I found no study that isolates serif vs sans numerals at display size on phones; the Richardson 2022 book may contain relevant material but its findings were not accessible.
- Fraunces' OpenType feature list (tnum/pnum/lnum/onum) is not stated in its README; the figure sets must be verified in a browser with `font-variant-numeric: tabular-nums` before relying on them.
- Söhne (Klim), GT Alpina (Grilli Type), Tiempos, Inter Display and Geist: I could not retrieve foundry pages documenting their figure sets in this session; check each foundry's OpenType feature list. Grilli's GT Alpina page has an OpenType section but it was not captured. — [Grilli Type, GT Alpina](https://grillitype.com/typeface/gt-alpina)

## 2. Number motion: counting, rolling and odometer digits; duration and easing; when counting becomes noise

### Takeaway
The best current web implementation of Family/Robinhood-style rolling digits is NumberFlow (`@number-flow/react`): dependency-free, React-native, per-digit spin via a digit-looping technique, Intl.NumberFormat-driven, respects `prefers-reduced-motion` by default, with `trend` and `continuous` options for direction and "pass through intermediate values". For direct manipulation the evidence says the number must track the finger with no animation at all while the gesture is live (apply the delta immediately), and only settle with a short (sub-300 ms, ease-out or tightly damped spring) animation when the finger lifts; counting animations that play on every frequent interaction become noise and make the interface feel slow.

### Cited Findings
- NumberFlow (`@number-flow/react`) is "Dependency-free. Accessible. Customizable.", "heavily inspired by the Family app", and uses a "digit looping technique" credited to Sam Selikoff; it transitions automatically when `value` changes. — [NumberFlow docs](https://number-flow.barvian.me/)
- NumberFlow timing props: `transformTiming`, `spinTiming` (falls back to `transformTiming`) and `opacityTiming`, each an `EffectTiming`. The documented examples use `duration: 750` with a `linear(...)` spring-sampled easing for transform and spin, and `duration: 350, easing: 'ease-out'` for opacity; no numeric defaults are published. — [NumberFlow docs](https://number-flow.barvian.me/)
- NumberFlow reduced motion: `respectMotionPreference` defaults to `true`; `animated` defaults to `true` and setting it `false` finishes any running animation; `useCanAnimate({ respectMotionPreference })` reports whether the browser supports the needed features and the user allows motion. — [NumberFlow docs](https://number-flow.barvian.me/)
- NumberFlow direction: `trend` defaults to `(oldValue, value) => Math.sign(value - oldValue)` (+1 all digits roll up, −1 all roll down, 0 each digit chooses its own direction); the `continuous` plugin makes transitions "appear to pass through in-between numbers" and has no effect when `trend` is 0; `digits` lets a position wrap (e.g. 59 → 00). — [NumberFlow docs](https://number-flow.barvian.me/)
- NumberFlow limits: `format` accepts `Intl.NumberFormatOptions` and `locales`; scientific/engineering notation, non-Latin digits and RTL are unsupported; backgrounds and borders do not scale smoothly during transitions; `willChange` defaults to `false` with a warning that excessive use increases memory. — [NumberFlow docs](https://number-flow.barvian.me/)
- Robinhood's open-source Android `Ticker` is "a simple Android UI component for displaying scrolling text", odometer-like, with an ordered character list controlling the path between digits and "wrap-around animation when it's faster"; examples set `ticker_animationDuration="1500"` and `setAnimationDuration(500)`, `preferredScrollingDirection="any"`, and `OvershootInterpolator`. — [robinhood/ticker on GitHub](https://github.com/robinhood/ticker)
- Emil Kowalski: "Your animations should also usually be shorter than 300ms"; `ease-out` "starts fast and slows down at the end" and suits snappy UI; "Before you add an animation, you should also consider how often the user will see it"; keyboard-initiated and frequent actions should not be animated; too many animations mean "The user then becomes overwhelmed and animations lose their impact." — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations)
- Rauno Freiberg: apply gesture deltas immediately rather than playing a 0→1 animation after a threshold; animations should be interruptible; gestures should keep momentum and throw angle; skip animation for high-frequency actions (command menus, context menus used "hundreds" or "thousands" of times a day); a bookmarking tool's animations felt sluggish after "a couple of days"; keep a drag active even when the finger moves off a small control such as a slider. — [Rauno Freiberg, Invisible Details of Interaction Design](https://rauno.me/craft/interaction-design)
- Apple HIG: "Aim for brevity and precision in feedback animations"; "In apps, generally avoid adding motion to UI interactions that occur frequently"; "Let people cancel motion"; "Add motion purposefully … Gratuitous or excessive animation can distract people and may make them feel disconnected or physically uncomfortable." — [Apple HIG, Motion](https://developer.apple.com/design/human-interface-guidelines/motion)
- Apple HIG on the Digital Crown: "Provide visual feedback in response to Digital Crown interactions … If you don't provide visual feedback, people are likely to assume that turning the Digital Crown has no effect"; "Update your interface to match the speed with which people turn the Digital Crown … Avoid updating content at a rate that makes it difficult for people to select values." — [Apple HIG, Digital Crown](https://developer.apple.com/design/human-interface-guidelines/digital-crown)
- Open-source recreations of the Family number animation animate "digit-by-digit with an iOS-style spring, blurring only the digits that change" and keep unchanged leading digits still. — [animated-blur-number (ecosyste.ms index)](https://awesome.ecosyste.ms/projects/github.com%2Fserafimcloud%2Fanimated-blur-number); [expo-number-transition-animation](https://awesome.ecosyste.ms/projects/github.com%2Farunabhverma%2Fexpo-number-transition-animation)

### Inferences
- Two regimes for the headline figure. (a) While the dial is turning: no NumberFlow animation; set `animated={false}` (or bypass it) and write the deterministic figure every frame so the number is glued to the finger, in tabular figures. (b) On release, and when the Monte Carlo result lands: re-enable animation and let NumberFlow roll the digits over roughly 250–400 ms with an ease-out or a critically damped spring; `trend` should follow the sign of the change so the roll direction encodes "more" or "less". This matches Rauno's "apply gesture deltas immediately" and Emil's sub-300 ms rule, and Apple's "match the speed with which people turn".
- Counting becomes noise when it (i) runs on every tick of a frequently used control, (ii) exceeds ~300 ms, or (iii) rolls digits that did not change. Keep leading unchanged digits still (Family pattern), only animate on commit, and reserve the longer 750 ms-style roll for one-off reveals (the first answer, the end of a Monte Carlo run).
- Confidence (%) and "how long it lasts" are low-digit-count values; they can use the same component with `continuous` so a move from 71 % to 84 % visibly passes through the intermediate values, which reads as "measured" rather than "swapped".

### Gaps
- No published duration/easing defaults for NumberFlow; the library documents example values only.
- I could not retrieve a primary write-up from Stripe, Linear, Arc or Amie on their number-counting animations; only Family's influence is documented (via NumberFlow and the recreations).
- No controlled study on perceived latency thresholds for rolling digits was found; the ~300 ms figure is practitioner guidance (Kowalski) not experimental evidence.

## 3. Motion design systems worth copying: spring values, inertia, reduced-motion patterns

### Takeaway
Two systems publish usable numbers. Material 3 Expressive (AndroidX source) separates *spatial* springs (bounds/shape; default stiffness 380, damping ratio 0.8; fast 800/0.6; slow 200/0.8) from *effects* springs (colour/alpha; always critically damped, damping 1.0; stiffness 1600 default, 3800 fast, 800 slow). Motion (ex-Framer Motion) ships inertia for flicks (`power` 0.8, `timeConstant` 700, bounce stiffness 500/damping 10) and a `MotionConfig reducedMotion="user"` mode that disables transform/layout animation while keeping opacity and colour, which is exactly the "crossfade instead of move" pattern Apple recommends. Apple's reduced-motion list (tighten springs, track gestures directly, avoid z-axis depth animation, replace x/y/z transitions with fades, avoid blur animation) is the most specific guidance for a 3D instrument.

### Cited Findings
- Material 3 Expressive motion tokens (AndroidX, generated code `v0_14_0`): `SpringDefaultSpatialDamping 0.8`, `SpringDefaultSpatialStiffness 380`; `SpringFastSpatialDamping 0.6`, `SpringFastSpatialStiffness 800`; `SpringSlowSpatialDamping 0.8`, `SpringSlowSpatialStiffness 200`; `SpringDefaultEffectsDamping 1.0`, `SpringDefaultEffectsStiffness 1600`; `SpringFastEffectsDamping 1.0`, `SpringFastEffectsStiffness 3800`; `SpringSlowEffectsDamping 1.0`, `SpringSlowEffectsStiffness 800`. — [ExpressiveMotionTokens.kt, AndroidX](https://android.googlesource.com/platform/frameworks/support/+/androidx-main/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/tokens/ExpressiveMotionTokens.kt)
- Material 3 `MotionScheme`: the spatial spec "is designed to be applied to animations that may change the shape or bounds of the component"; the effects spec "is designed to be applied to animations that do not change the shape or bounds of the component", e.g. colour. Standard scheme is for "utilitarian UI elements and recurring interactions … a linear motion feel"; Expressive is "for prominent UI elements and hero interactions". — [MotionScheme.kt, AndroidX](https://android.googlesource.com/platform/frameworks/support/+/androidx-main/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/MotionScheme.kt)
- Motion (React) spring options: `damping` 10, `mass` 1, `bounce` 0.25 (0 = critically damped, negative = overdamped), `restSpeed` 0.1, `restDelta` 0.01, `visualDuration` overrides `duration`; setting `stiffness`/`damping`/`mass` overrides `bounce`/`duration`; physics springs "incorporate the velocity of existing gestures or animations"; tween default duration 0.3 s (0.8 s with multiple keyframes). The fetched page listed `stiffness` default as 1, which conflicts with earlier Framer Motion docs (100) and should be verified. — [Motion, React transitions](https://motion.dev/docs/react-transitions)
- Motion `dragTransition` is always `type: "inertia"`, with `power` 0.8, `timeConstant` 700, `bounceStiffness` 500, `bounceDamping` 10, and `min`/`max` bounds. — [Motion, React transitions](https://motion.dev/docs/react-transitions)
- Motion accessibility: `useReducedMotion()` returns a boolean from the OS setting; `<MotionConfig reducedMotion="user">` "Automatically disables transform animations (such as x/y/scale) and layout animations on all motion components. Other values, such as opacity and backgroundColor, still animate." Recommended patterns: swap `x` for `opacity`, disable autoplay, set parallax motion values to a static 0. — [Motion, React accessibility](https://motion.dev/docs/react-accessibility)
- Apple HIG, Reduce Motion best practices: "Tightening animation springs to reduce bounce effects; Tracking animations directly with people's gestures; Avoiding animating depth changes in z-axis layers; Replacing transitions in x-, y-, and z-axes with fades to avoid motion; Avoiding animating into and out of blurs"; also reduce "zooming, scaling, and peripheral motion". — [Apple HIG, Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- Apple exposes a separate "Prefer Cross-Fade Transitions" setting: `accessibilityPrefersCrossFadeTransitions` is true when Reduce Motion or Prefer Cross-Fade is on; UI "should avoid Slide animations and prefer Cross-Fade transitions instead". — [Apple Developer, accessibilityPrefersCrossFadeTransitions](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilitypreferscrossfadetransitions); [UIKit prefersCrossFadeTransitions](https://developer.apple.com/documentation/uikit/uiaccessibility/preferscrossfadetransitions)
- Apple HIG, Motion: "Make motion optional … avoid using it as the only way to communicate important information … supplement visual feedback by also using alternatives like haptics and audio"; for visionOS, "avoid showing objects that oscillate in a sustained way … around 0.2 Hz", "Consider using fades when you need to relocate an object", "In general, avoid letting people rotate a virtual world". — [Apple HIG, Motion](https://developer.apple.com/design/human-interface-guidelines/motion)
- WCAG 2.2 SC 2.3.3 Animation from Interactions (AAA): "Motion animation triggered by interaction can be disabled" unless essential; motion animation means intermediate steps creating the look of movement, and "Color, blur, and opacity changes don't count unless they change an element's apparent size, shape, or position"; technique C39 uses `prefers-reduced-motion`. — [WCAG 2.2 Understanding 2.3.3](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)
- web.dev: `prefers-reduced-motion` returns `no-preference` or `reduce`; CSS responds automatically but JS animations must listen for `matchMedia(...).addEventListener('change')`; animation CSS can be put in a stylesheet loaded with `media="(prefers-reduced-motion: no-preference)"` so opted-out users never download it. — [web.dev, prefers-reduced-motion](https://web.dev/articles/prefers-reduced-motion)
- iOS scroll deceleration: `UIScrollView.decelerationRate` normal is 0.998, i.e. the view "loses 0.2% of its velocity per millisecond"; velocity decays exponentially; WWDC18 "Designing Fluid Interfaces" introduced a projection function whose result differs by under 1 % from the exact exponential-decay derivation. — [Deceleration mechanics of UIScrollView](https://medium.com/@esskeetit/scrolling-mechanics-of-uiscrollview-142adee1142c); [Gestures in Fluid Interfaces — On Intent and Projection](https://medium.com/ios-os-x-development/gestures-in-fluid-interfaces-on-intent-and-projection-36d158db7395)
- Josh Comeau's spring primer: mass is "the heft of the thing we're moving", tension/stiffness "how tightly-wound the spring is", friction/damping "a characteristic of the universe the spring exists within"; without friction springs oscillate forever; high friction suits smooth non-bouncy motion. No recommended defaults. — [Josh Comeau, A Friendly Introduction to Spring Physics](https://www.joshwcomeau.com/animation/a-friendly-introduction-to-spring-physics/)
- Emil Kowalski recommends springs ("I highly suggest playing around with spring animations in your projects") and notes Vercel's dashboard tab animation dropped frames until moved to CSS; Raycast "has no animations" and "feels right". — [Emil Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations)

### Inferences
- Recommended spring set for the instrument, mapped from Material's published tokens: dial/drum settling after release = spatial default (stiffness 380, damping ratio 0.8 → slight, quick overshoot that reads as mass); snapping to a detent after a flick = spatial fast (800/0.6) only if a visible bounce is wanted, otherwise 800/0.8; headline, confidence tint, band fills and background dawn = effects springs (critically damped, 1600 default) so nothing that encodes a value ever overshoots the truth. Overshoot on a *number* would momentarily show a wrong figure, which breaks the "honest" criterion.
- Flick inertia: Motion's inertia (`power` 0.8, `timeConstant` 700) or the iOS 0.998/ms decay are interchangeable starting points; project the release velocity to a target angle, then clamp to the nearest detent so the drum always lands on a legal value.
- Under reduced motion follow Apple's list literally: rotation and parallax become crossfades (opacity only), springs become critically damped or instant, the dawn background changes by colour not by movement, and the dial still tracks the finger directly ("tracking animations directly with people's gestures" is explicitly allowed). WCAG 2.3.3 treats colour/opacity changes as not being motion, so a crossfade-only mode is compliant.
- Use `MotionConfig reducedMotion="user"` if Motion is adopted; otherwise a single `matchMedia('(prefers-reduced-motion: reduce)')` hook feeding both the CSS custom properties and the Canvas/WebGL loop.

### Gaps
- Material's official site (m3.material.io) could not be fetched; values above come from the AndroidX source, which is authoritative for Compose but the web/Flutter ports disagree on some damping values (0.73 vs 0.8). — [material_expressive on pub.dev](https://pub.dev/packages/material_expressive)
- Motion's `stiffness` default was reported as 1 by the fetched page; treat as unverified.
- I did not find published motion specs for Linear, Arc, Family, Amie or Vercel; the evidence about them is second-hand (Kowalski, Rauno).
- No source gives measured numbers for "how many users enable reduced motion".

## 4. Building a rotational control on touch: pointer events, capture, touch-action, flick physics, haptics

### Takeaway
A web dial is: one element with `touch-action: none` (set on the dial itself, since the browser intersects `touch-action` up the ancestor chain and ignores changes made after a gesture starts), `pointerdown` → `setPointerCapture`, angle from `atan2` on `pointermove`, release velocity → inertia → nearest detent. The scroll-vs-rotate conflict on a vertical phone is solved by making the whole home non-scrolling (the brief's premise) so the dial can own all touches; if any scrolling surface remains, use `pan-y` on it and `none` on the dial, and accept that iOS will `pointercancel` a touch the moment it decides it is a scroll. Haptics are Android-only in practice: `navigator.vibrate` needs sticky user activation and is unsupported in Safari; the iOS `<input type="checkbox" switch>` haptic side-effect worked from iOS 17.4 but has since been restricted to user activation and, per the library that exploited it, patched in iOS 26.5.

### Cited Findings
- `touch-action` values: `none`, `pan-x`, `pan-y`, `pan-left/right/up/down`, `pinch-zoom`, `manipulation` (alias for `pan-x pan-y pinch-zoom`, which also removes the click delay). The browser "intersects the touch-action values of the touched element and all its ancestors, up to the element that implements the gesture"; "changes to touch-action made after a gesture starts have no effect on that gesture". With Pointer Events, the browser sends `pointercancel` when it starts handling a touch gesture itself. Accessibility warning: `touch-action: none` "may inhibit operating a browser's zooming capabilities" — use it only on elements that provide their own dragging/zooming. — [MDN, touch-action](https://developer.mozilla.org/en-US/docs/Web/CSS/touch-action)
- `pointercancel` fires when "the browser determines that there are unlikely to be any more pointer events", including when, after `pointerdown`, the pointer is used to pan, zoom or scroll the viewport, when `touch-action` prevents the input from continuing, on orientation change, on palm rejection, or when too many simultaneous pointers exist; it is followed by `pointerout` and `pointerleave`. — [MDN, pointercancel](https://developer.mozilla.org/en-US/docs/Web/API/Element/pointercancel_event)
- `setPointerCapture` makes an element keep receiving pointer events "even when contact leaves it through scrolling or panning"; touchscreen browsers set an implicit capture on `pointerdown` that is released after `pointerup`/`pointercancel`. — [MDN, setPointerCapture](https://developer.mozilla.org/en-US/docs/Web/API/Element/setPointerCapture); [web package docs on implicit capture](https://pub.dev/documentation/web/latest/web/Element/setPointerCapture.html)
- A scroll that starts during a captured pointer still fires `pointercancel` and ends the interaction (Babylon.js report). — [Babylon.js forum](https://forum.babylonjs.com/t/pointer-capture-failing-for-babylon-pointer-observable-during-a-scroll-event/43253)
- Rauno Freiberg: for small controls like sliders, "Keep the drag active even when the finger moves off the control"; radial menus "keep distance and size equal for every option, which builds muscle memory". — [Rauno Freiberg](https://rauno.me/craft/interaction-design)
- Apple HIG, Digital Crown: by default the system "provides linear haptic detents — or taps — as people turn the Digital Crown a specific distance"; "When anchoring interactions to the Digital Crown, also be sure to back them up with corresponding touch screen interactions"; "if the default detents don't match your app's animation — turn off the detents". — [Apple HIG, Digital Crown](https://developer.apple.com/design/human-interface-guidelines/digital-crown)
- Apple HIG, Playing haptics: "Selection haptics provide feedback while the values of a UI element are changing"; the watchOS "Click" haptic "Provides the sensation of a dial clicking … Overusing the click haptic tends to diminish its utility and can even be confusing when clicks overlap each other"; "Avoid overusing haptics … Often, the best haptic experience is one that people may not be conscious of, but miss when it's turned off"; "Make haptics optional"; "match the intensity and sharpness of a haptic with the intensity and sharpness of the animation it accompanies". Standard iOS sliders and pickers "play Apple-designed system haptics by default". — [Apple HIG, Playing haptics](https://developer.apple.com/design/human-interface-guidelines/playing-haptics)
- `navigator.vibrate(pattern)`: pattern is alternating vibrate/pause ms; returns false on invalid parameters; requires sticky user activation; marked "Limited availability … does not work in some of the most widely used browsers"; silent on devices without vibration and may be suppressed in Silent/Do Not Disturb. — [MDN, Navigator.vibrate](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/vibrate)
- iOS Safari haptic workaround: `ios-haptics` places a hidden `<input type="checkbox" switch>` over the element; Safari plays its switch haptic when it toggles. The README states it "only works on ios 17.4 to 26.4, as apple patched it in ios 26.5." — [ios-haptics README](https://unpkg.com/ios-haptics@3.1.1/README.md); Ionic's feature request describes the same mechanism — [ionic-framework #29942](https://github.com/ionic-team/ionic-framework/issues/29942)
- WebKit bug 285120, "haptic feedback for <input type=checkbox switch> should require user activation", was RESOLVED FIXED on 2025-01-03 (commit 288403@main) after a report that "it is possible to exploit this feature and generate vibrations from JavaScript". — [WebKit Bugzilla 285120](https://bugs.webkit.org/show_bug.cgi?id=285120)
- Flick physics references: iOS normal deceleration 0.998 per ms (exponential decay) and the WWDC18 projection function; Motion's inertia defaults (`power` 0.8, `timeConstant` 700). — [Deceleration mechanics of UIScrollView](https://medium.com/@esskeetit/scrolling-mechanics-of-uiscrollview-142adee1142c); [Motion, React transitions](https://motion.dev/docs/react-transitions)

### Inferences
- Gesture handler sketch for a ring/drum: `onPointerDown` → `e.currentTarget.setPointerCapture(e.pointerId)`, record `atan2(y−cy, x−cx)` and timestamp; `onPointerMove` → delta angle (unwrap across ±π), accumulate into a value, write the cheap deterministic answer immediately (see §7), keep a 3–5 sample velocity window; `onPointerUp` → project `angularVelocity × timeConstant` (≈0.7 s) and round to the nearest detent; `onPointerCancel` → treat as release at the current value so the plan is never left half-set. `touch-action: none` on the dial, `overscroll-behavior: none` and `overflow: hidden` on the home so iOS never starts a pan.
- Because the home is one non-scrolling screen, the "scroll vs rotate" conflict is designed away; the remaining risk is iOS Safari's own edge gestures (back-swipe from the left edge, bottom bar) which cannot be suppressed, so keep the ring's active area at least ~24 px from the screen edges.
- Haptics: use `navigator.vibrate(4–8 ms)` per detent on Android, gated behind a setting (Apple's "make haptics optional"), and expect none on iOS; design the detent feedback visually and (optionally) with a very short click sound so iPhone users still feel the stops. Do not build on the iOS switch trick: it is restricted to user activation and reported patched.
- The Apple detent guidance translates to a detent per meaningful step (one year of stop age, £50 a month, £5k of pot) with the click suppressed when the user flicks fast (clicks "overlap each other").

### Gaps
- I did not find a primary source for how iOS Safari (as opposed to Chrome Android) behaves when `touch-action: none` is set on a child of a scrolling page during a very fast initial touch; practitioner reports suggest it works but testing on device is required.
- Apple's own confirmation of the iOS 26.5 patch of the switch haptic was not found; the claim rests on the `ios-haptics` README.
- No measured data on `navigator.vibrate` latency on Android relative to the visual detent.

## 5. Rendering a drum, ring or orrery on a phone: CSS 3D vs Canvas 2D vs WebGL, iOS Safari bugs, GPU memory, when "fake 3D" is right

### Takeaway
For a single rotating object with a few dozen elements, CSS transforms and a 2D canvas are cheaper, smaller and less fragile than WebGL; three.js alone is ~86–125 kB gzipped and brings context-loss and memory-pressure failure modes on iOS. CSS 3D is viable for a drum of faces as long as nothing in the 3D subtree uses `overflow`, `filter`/`backdrop-filter`, `mask` or `isolation` (those flatten `preserve-3d` by design in WebKit) and nothing inside is `position: fixed`. A 2D canvas "fake 3D" (project the ring/drum yourself, draw with transforms and gradients) is the right call when the object is a single instrument, the numerals must stay crisp 2D text, and you want deterministic 60 fps on a three-year-old phone; it also sidesteps every preserve-3d bug. Reserve WebGL for an atmospheric background only if a CSS gradient cannot do it.

### Cited Findings
- web.dev animations guide: restrict animations to `opacity` and `transform` to stay on the compositor; animating `top`/`left` dropped 50 % of frames in the example while the `transform` version dropped 1 %; blur/shadow effects take longer to paint; `will-change` promotes a layer and "Layer creation can cause other performance issues", so apply it shortly before a change and remove it after. — [web.dev, Animations guide](https://web.dev/articles/animations-guide)
- WebKit bug 48386: "You have to flatten in order to clip, so overflow: style overrides preserve-3d" (Simon Fraser, by design, 2010). — [WebKit Bugzilla 48386](https://bugs.webkit.org/show_bug.cgi?id=48386); follow-up proposal to switch off preserve-3d for elements whose styles force flattening — [WebKit Bugzilla 83337](https://bugs.webkit.org/show_bug.cgi?id=83337)
- Blink intent-to-ship on grouping properties notes WebKit "fails to flatten for backdrop-filter, isolation and mask", i.e. WebKit's behaviour differs from Gecko/Blink for those properties in a `preserve-3d` tree. — [blink-dev, Align with Gecko and spec on grouping properties](https://groups.google.com/a/chromium.org/g/blink-dev/c/cubTsTuZWEY)
- A non-`none` `transform` on an ancestor makes it the containing block for `position: fixed` descendants, so fixed children stop being positioned to the viewport. — [Gist by claus](https://gist.github.com/claus/622a938d21d80f367251dc2eaaa1b2a9)
- WebKit crops non-empty `position: fixed` content taller than the viewport to `100dvh` on iOS (bug 253399); `svh`/`dvh` resolved equal when the tab bar was hidden (bug 261185, fixed November 2023); on iOS 26, fixed content below the new bottom browser controls is not rendered. — [WebKit Bugzilla 253399](https://bugs.webkit.org/show_bug.cgi?id=253399); [WebKit Bugzilla 261185](https://bugs.webkit.org/show_bug.cgi?id=261185); [Apple Developer Forums 800798](https://developer.apple.com/forums/thread/800798); [Apple Developer Forums 803987](https://developer.apple.com/forums/thread/803987)
- iOS canvas memory: WebKit enforces a total canvas memory budget; a console warning at a 384 MB limit and "Total canvas memory use exceeds the maximum limit" failures appeared from iOS 12; a reported workaround is to set a dead canvas's width and height to 0 before dropping references. — [WebKit Bugzilla 195325](https://bugs.webkit.org/show_bug.cgi?id=195325)
- Resizing an on-screen WebGL canvas in iOS Safari leaked memory until the page reached 1.25 GB and was killed; reported fixed in iOS 14.3. — [Apple Developer Forums 668999](https://developer.apple.com/forums/thread/668999)
- Determining the maximum canvas size on iOS: the usual WebGL draw-buffer binary search loops forever on iOS; the `canvas-size` probe approach that reads pixels back at decreasing sizes works on all devices. — [geOps, Determining maximum HTML Canvas sizes](https://geops.com/en/blog/html-canvas-for-raster-exports)
- A mobile-game guide reports iOS Safari can lose the WebGL context under memory pressure, on app switching, or after time in the background, and recommends handling `webglcontextlost` (with `preventDefault`) and `webglcontextrestored`; its "~256 MB GPU" figure is unsourced. — [iOS Safari gotchas for mobile web games](https://abratabia.com/mobile-web-games/ios-safari-gotchas.php) (secondary source)
- react-three-fiber performance docs: the default loop "runs 60 times a second" and "drains batteries the most"; `<Canvas frameloop="demand">` renders only when `invalidate()` is called ("it merely requests a new frame"); `PerformanceMonitor` lowers `dpr` (examples 1, 1.5, 2) on sustained FPS decline and `performance={{ min: 0.5 }}` scales resolution; each mesh is a draw call, "no more than 1000 as the very maximum"; creating 510 `TextGeometry` at once caused "approximately 1.5 seconds of pure jank" on an M1 until time-sliced with `startTransition`. — [R3F, Scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance)
- three.js size: the r181 build PR lists the full ESM WebGL build at roughly 86 kB minified+gzipped (WebGPU ~171 kB); a forum report measured a minimal scene at 117.77 → 125.03 kB gzipped moving r180 → r181. — [three.js PR 32154](https://github.com/mrdoob/three.js/pull/32154); [three.js forum on 0.181 size](https://discourse.threejs.org/t/8kb-gzipped-size-increase-in-0-181-0-recommendation-on-tooling-to-analyze-package-size/87880)
- Comparative study (2024/5, iOS and Android, animated circles): Canvas extends usability to higher object counts; WebGL is most stable at 5,000–10,000 objects; HTML/CSS goes through layout/paint/composite. Another paper found WebGL "especially on older hardware, can cause significant processor load" while traditional web technologies gave the most stable display. — [MDPI J. Imaging](https://www.mdpi.com/2313-433X/12/1/45); [TU Wien comparative study](https://www.cvast.tuwien.ac.at/sites/default/files/bakkarbeit/Krug/index.html)
- Canvas 2D performance checklist (web.dev, 2011 but still valid): pre-render static parts to an offscreen canvas, batch paths, minimise state changes, redraw only changed regions, layer a static background canvas under an animated one, avoid `shadowBlur`, round coordinates, use `requestAnimationFrame`. — [web.dev, Improving HTML5 Canvas performance](https://web.dev/articles/canvas-performance)
- Safari's `requestAnimationFrame` is capped at 60 Hz unless the "Prefer Page Rendering Updates Near 60fps" flag is off on ProMotion devices; WKWebView-based apps stay at 60 Hz; reports for iOS 26 conflict. — [WebKit Bugzilla 294338](https://bugs.webkit.org/show_bug.cgi?id=294338); [WebKit Bugzilla 173434](https://bugs.webkit.org/show_bug.cgi?id=173434)
- Apple HIG: "maintaining a consistent frame rate of 30 to 60 fps typically results in a smooth, visually appealing experience" (games guidance). — [Apple HIG, Motion](https://developer.apple.com/design/human-interface-guidelines/motion)

### Inferences
- Decision rule: (1) CSS 3D if the drum's faces are DOM (so numerals are real text, selectable, screen-readable) and the faces need no clipping/blur/backdrop effects — the current project already has a `rotateX` ring component, so this path is proven in this codebase; (2) Canvas 2D for the ring/orrery/pie and the projection bands, drawn at `devicePixelRatio` clamped to 2, with static layers cached offscreen; (3) WebGL only for a background that genuinely needs shading, with `frameloop="demand"`, context-loss handlers and a CSS-gradient fallback. Budget: the whole home should be well under the ~100 kB gzipped that three.js alone would add.
- The iOS fixed/transform rules mean: never put the sheet/overlay layer inside the transformed instrument subtree; keep `position: fixed` surfaces as siblings at the root, sized with `100dvh` and tested on iOS 26's bottom bar.
- A "fake 3D" canvas drum (draw the visible faces with `scaleY(cos θ)` and a gradient, plus a 2D text overlay for the active value) gives the owner's 3D feel without any `preserve-3d`, and its reduced-motion variant is simply "no inter-frame tween".
- 60 fps on a three-year-old phone is realistic for CSS transforms and a modest canvas; Safari's 60 Hz cap means there is no point targeting 120 Hz on iPhone.

### Gaps
- No like-for-like battery measurement of CSS vs Canvas vs WebGL on current phones was found; the comparisons are object-count scaling studies and qualitative texts.
- No WebKit bug specifically on `backdrop-filter` × `preserve-3d` was found; the Blink thread says WebKit *fails to flatten* (i.e. the effect may silently misrender), so test any glass/blur effect near the 3D subtree.
- No current primary figure for iOS GPU memory limits per page; the 384 MB canvas budget is the only documented number.

## 6. Accessible dials and radial controls: ARIA, keyboard, VoiceOver/TalkBack, touch targets, WCAG 2.5.7/2.3.3, real products

### Takeaway
Expose the dial as `role="slider"` (or six sliders, one per face) with `aria-valuenow/min/max`, `aria-valuetext` ("£2,400 a month"), and the APG keyboard map (arrows ±step, PageUp/PageDown ±big step, Home/End) — but do not rely on `role="slider"` alone on mobile: VoiceOver and TalkBack intercept the swipe-up/down and volume-key gestures and a custom widget never receives them, so the dial must be backed by a real `<input type="range">` (with a non-zero `step`) or by visible +/− buttons, which also satisfy WCAG 2.5.7's mandatory non-drag alternative. Targets: 24 × 24 CSS px minimum (WCAG 2.5.8 AA), 44 × 44 pt as Apple's default, 28 × 28 pt as its floor, with 12–24 pt spacing. No public documentation of how Nest, Apple Clock, Headspace or Oura make ring controls accessible was found; the Nest app has a documented history of VoiceOver complaints.

### Cited Findings
- WAI-ARIA APG slider pattern: keyboard — Right/Up Arrow increase by one step, Left/Down Arrow decrease, Home/End to first/last value, Page Up/Down (optional) by a larger step; required `role="slider"`, `aria-valuenow`, `aria-valuemin`, `aria-valuemax`, `aria-valuetext` "when the numeric value isn't user-friendly", `aria-labelledby` or `aria-label`, `aria-orientation` for vertical. Warning: "some touch-based assistive technologies may have difficulty with slider widgets. Their gestures may not generate the output needed to change the value" and synthesising key events "is a new convention that not all assistive technologies fully support"; test on touch devices before production. — [WAI-ARIA APG, Slider pattern](https://www.w3.org/WAI/ARIA/apg/patterns/slider/)
- MDN slider role: `aria-valuenow` must stay within min/max; for custom sliders the component must update `aria-valuenow` itself. — [MDN, ARIA slider role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Roles/slider_role)
- Patrick H. Lauke (WebAIM list): `role="slider"` makes VoiceOver/TalkBack offer their hints, "However, as it's not a real actual slider, performing those actions by themselves has no effect"; JavaScript cannot detect Android volume keys; when AT is running it "consumes" swipe gestures so they never reach the page. — [WebAIM discussion 39122](https://webaim.org/discussion/mail_message?id=39122)
- Angular Material issue: VoiceOver on iOS announced "0%, adjustable. Swipe up or down with one finger to adjust the value" but the value did not change; the team moved to a native `<input type="range">`; a later finding was that even the native range failed when `step` was 0 and worked with `step` ≥ 1; fixed June 2023 ("fix voiceover on ios", PR #27302). — [angular/components #15037](https://github.com/angular/components/issues/15037)
- VoiceOver adjustable controls (native): one-finger swipe up/down changes the value, announcing each step; values should be descriptive strings ("3 stars", "1 minute 58 seconds of 4 minutes 7 seconds"); at the limit "VoiceOver then plays a soft sound to signal that the limit was reached". — [Accessible Sliders and Adjustable Controls](https://d-ronnqvist.github.io/accessible-sliders-and-adjustable-controls)
- WCAG 2.2 SC 2.5.7 Dragging Movements (AA): "All functionality that uses a dragging movement for operation can be achieved by a single pointer without dragging", unless essential or user-agent-determined. Acceptable alternatives include tapping the track, up/down buttons, or entering a value in a text field beside a slider or colour wheel. "Keyboard equivalence alone doesn't satisfy 2.5.7 unless the keyboard operation also offers controls that can be clicked or tapped"; the alternative "can't exclusively rely on a path-based gesture, such as swiping or 'flicking'". Technique G219; failure F108. — [WCAG 2.2 Understanding 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)
- WCAG 2.2 SC 2.5.8 Target Size (Minimum) (AA): targets at least 24 × 24 CSS px, except where a 24 px circle centred on each undersized target does not intersect another target's circle (spacing), or an equivalent control exists, or the target is inline, user-agent controlled, or essential. — [WCAG 2.2 Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- Apple HIG: iOS default control size 44 × 44 pt, minimum 28 × 28 pt; "about 12 points of padding around elements that include a bezel. For elements without a bezel, about 24 points"; "Offer alternatives to gestures … if you use a swipe gesture to dismiss a view, also make a button available"; "avoid custom multifinger and multihand gestures"; "Convey information with more than color alone". — [Apple HIG, Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- Apple HIG, Motion: "Make motion optional … avoid using it as the only way to communicate important information". — [Apple HIG, Motion](https://developer.apple.com/design/human-interface-guidelines/motion)
- WCAG 2.2 SC 2.3.3 (AAA): interaction-triggered motion animation must be disableable unless essential; `prefers-reduced-motion` is the sufficient technique. — [WCAG 2.2 Understanding 2.3.3](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)
- Nest app accessibility: AppleVis users reported the current-temperature reading "isn't labeled right", a newer version being "even less accessible than an earlier one", and later improvement; a 2026 Double Tap episode calls Google's discontinuation of cloud support for first/second-generation Nest thermostats "a major accessibility blow for blind users". — [AppleVis forum thread](https://applevis.com/forum/smart-home-tech/which-smart-thermostats-have-accessible-ios-apps); [Double Tap, Apple VoiceOver turns 20 + Google Nest accessibility disaster](https://doubletaponair.com/apple-voiceover-turns-20-google-nest-accessibility-disaster/)

### Inferences
- Accessible architecture for a six-faced instrument: render six real `<input type="range">` elements (one per input; for couples, twelve, or six with a partner toggle) visually hidden but focusable, each with `step` ≥ 1, `aria-valuetext` in plain English ("Stop at 62", "£2,400 a month after tax", "Pension pot £310,000"), and drive the visible dial from their values. The visible ring is `aria-hidden` decoration bound to the active input. This gives VoiceOver/TalkBack their native adjustable behaviour (swipe up/down, volume keys), gives keyboards the APG map for free, and gives Playwright a stable handle.
- The WCAG 2.5.7 alternative must be pointer-operable: a tap on a detent mark should set the value; +/− at either end of the active arc (≥ 44 px) or a tap-to-type field on the headline itself. A tap-to-type field also serves people who know their figures and do not want to turn a dial through £300,000.
- Hit targets on a ring: the face selector segments must each be ≥ 44 × 44 px in their touch area even if the drawn arc is thinner; the active drag region should be a wide annulus (e.g. 56 px) not the drawn 4 px line (Rauno: keep the drag active off the control).
- Focus management: one roving tabindex per face selector (arrow keys move between faces, Enter/Space focuses the face's range), then the range itself; announce the live headline through a polite `aria-live` region that updates only on commit (pointer up / key up), never per frame.

### Gaps
- No public documentation or audits were found for Apple Clock's timer dial, Headspace's timer ring or Oura's ring controls; Apple Clock's countdown picker is a native wheel picker (my understanding, unverified here).
- The APG itself has no radial/dial example; the vertical temperature slider is the closest.
- No source describes TalkBack's behaviour with custom web sliders beyond the volume-key limitation.

## 7. Live-output coupling: cheap deterministic figure at frame rate, Monte Carlo in a worker, React 19 patterns

### Takeaway
Pattern: "fast approximate now, precise soon". On each pointer move, write the input into a ref and compute the deterministic answer synchronously (the engine's `drawdown`/`runPath` on one path is cheap), painting it via a `requestAnimationFrame`-coalesced update; post the plan to the Monte Carlo worker (`horizon/src/lib/mc.worker.ts`, 2,000 paths) with a generation id, drop stale results, and let `useDeferredValue` keep the heavy React subtree (bands, confidence) one step behind the input without blocking it. React's docs are explicit that `useDeferredValue` optimises *rendering* and adapts to device speed, while debounce/throttle still matter for *work outside rendering* such as the worker round-trip.

### Cited Findings
- `useDeferredValue`: React "first re-renders with the old deferred value, then tries a background re-render with the new value"; the background render is interruptible and restarts on new input; "Input events are prioritized over it"; there is no fixed delay; the deferred child must be wrapped in `memo` or the optimisation is lost; `initialValue` option exists; "useDeferredValue is better suited to optimizing rendering because it is deeply integrated with React itself and adapts to the user's device" but "If the work you're optimizing doesn't happen during rendering, debouncing and throttling are still useful … You can also use these techniques together." Inside a Transition it returns the new value immediately. — [React docs, useDeferredValue](https://react.dev/reference/react/useDeferredValue)
- Slider + worker flooding: "As the slider is dragged, requests pile up on the worker for every mouse move event, and the worker keeps working on them long after dragging stops" — only the latest value should be computed. — [Parallelizing JavaScript workloads with Plotly.js and webpack-worker](https://medium.com/webpack/parallelizing-javascript-workloads-building-high-performance-graphs-with-plotly-js-a9772764afe)
- Fintech Monte Carlo in workers: the costly step was aggregation and sorting, not the random walk; `Float32Array` "cuts memory use in half"; transferring buffers reduces copy overhead. — [Parallel JavaScript for Fintech Monte Carlo](https://medium.com/@nttp/parallel-javascript-for-fintech-monte-carlo-e3b036d3d2d8)
- React + Web Worker setup: create the worker in `useEffect`, hold it in a ref, and note messages are structured-cloned unless transferables are used. — [OneUptime, Web Workers in React](https://oneuptime.com/blog/post/2026-01-15-react-web-workers-cpu-intensive-tasks/view)
- `requestAnimationFrame` "schedules a function to run before the next available screen repaint"; store the id in a ref so the loop can be cancelled on unmount. — [OpenReplay, requestAnimationFrame in React](https://blog.openreplay.com/use-requestanimationframe-in-react-for-smoothest-animations/); [Educative, requestAnimationFrame with React](https://www.educative.io/answers/how-to-use-requestanimationframe-with-react)
- R3F: `startTransition`/`useTransition` time-slice expensive work; the TextGeometry benchmark went from ~1.5 s of jank to a steady ~60 fps when work was transitioned; mutated values are invisible to React so call `invalidate()` after them. — [R3F, Scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance)
- Project facts (from the repository): one simulation function `runPath(X, acc, ret, want)` serves both `drawdown` (deterministic) and `runMonteCarlo`; MC runs in a web worker with 2,000 paths and a main-thread fallback; `runAssertions` requires MC == deterministic at zero volatility; `successProb`, `successProbWithCuts`, `successLifetime` are the confidence outputs. — `/home/user/Retire-Lens-2/CLAUDE.md`; worker at `/home/user/Retire-Lens-2/horizon/src/lib/mc.worker.ts`; a second worker `/home/user/Retire-Lens-2/horizon/src/lib/insight.worker.ts` already exists for `levers`/insights.
- web.dev: keep per-frame work to compositor properties (`transform`, `opacity`); layout/paint properties dropped half the frames in the example. — [web.dev, Animations guide](https://web.dev/articles/animations-guide)

### Inferences
- Concrete loop: `pointermove` → `inputRef.current = value` → if no rAF pending, `requestAnimationFrame(() => { headline = drawdown(planFrom(inputRef)); paintHeadline(headline) /* direct DOM/canvas write via ref, not setState */ ; setCommitted(inputRef.current) /* low-priority state for the React tree */ })`. The dial rotation itself is a `transform` written to the element style in the same rAF, so the ring, the headline and the projection outline all move in the same frame.
- Worker protocol: `postMessage({ gen, plan })` at most every ~80–120 ms while dragging (throttle) and once on release; worker returns `{ gen, successProb, bands }`; ignore any result whose `gen` is older than the latest sent. Show the deterministic projection line immediately and crossfade the MC bands in when they arrive (effects spring, no movement), with a subtle "settling" state (e.g. reduced opacity of the confidence figure) while a run is in flight — React's own suggestion of dimming stale content.
- Keep React state out of the per-frame path: refs plus direct writes at frame rate; `useDeferredValue` on the committed plan for the heavy subtree; `useTransition` for face switches so the dial never blocks on a re-render of bands or the edge map.
- The existing engine's deterministic path should cost well under a frame for a single run (one plan, ~40 years); verify with a quick micro-benchmark on a mid-range Android (the three-year-old phone requirement) before committing to per-frame deterministic recompute; if it exceeds ~4 ms, precompute a coarse grid for the active face and interpolate during the drag, then snap to the exact value on release.

### Gaps
- No source directly documents the "approximate now, precise soon" pattern with Monte Carlo in a worker; it is assembled from the React docs, the Plotly worker-flooding report, and the project's own architecture.
- No published benchmark of this engine's `drawdown` per-call cost on a mid-range phone; must be measured.

## 8. Testability: driving a custom dial from Playwright and what to assert

### Takeaway
Playwright can drive the dial three ways: real pointer sequences via `page.mouse.move/down/move(…, { steps })/up` (which emit the pointer events a `touch-action: none` element listens to), keyboard via `locator.press('ArrowRight' | 'PageUp' | 'Home' | 'End')` on the focused range/slider, and synthetic `locator.dispatchEvent('pointerdown', …)` when exact event payloads are needed. Playwright's touchscreen emulation only supports `tap` (touchstart + touchend) and requires `hasTouch: true`, so flick/drag must be tested with the mouse path or hand-dispatched touch events. Assert on `aria-valuenow`/`aria-valuetext` of the backing range, the headline text, and the commit-only `aria-live` announcement — not on pixels.

### Cited Findings
- `mouse.move(x, y, { steps })` dispatches `n` interpolated `mousemove` events (default 1); `mouse.down()`/`mouse.up()` dispatch `mousedown`/`mouseup`; the docs show a drag traced through several `move` calls between `down` and `up`; `mouse.wheel` scrolls without waiting. — [Playwright, Mouse](https://playwright.dev/docs/api/class-mouse)
- Input docs: before a pointer action Playwright waits for the element to be attached, visible and stable and "receives pointer events at the action point"; `click({ force: true })` skips the checks; `dispatchEvent('click')` fires without a real pointer; `locator.dragTo()` and manual `hover → mouse.down → hover → mouse.up` for drags (move at least twice if the page relies on `dragover`); `locator.press` accepts `ArrowRight`, `ArrowUp`, `ArrowDown`, `Home`, `End`, `Enter`, `Tab`, `Escape`, with modifiers via `+`. — [Playwright, Actions/Input](https://playwright.dev/docs/input)
- Touchscreen: "limited to emulating tap gestures"; `tap(x, y)` dispatches `touchstart` then `touchend` with a single touch point; works only in contexts created with `hasTouch: true`; other gestures must be simulated by manually dispatching touch events. — [Playwright, Touchscreen](https://playwright.dev/docs/api/class-touchscreen)
- ARIA slider contract to assert against: `aria-valuenow` within `aria-valuemin`/`aria-valuemax`; custom sliders must update `aria-valuenow` themselves; arrow keys step by one. — [MDN, ARIA slider role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Roles/slider_role); [WAI-ARIA APG, Slider](https://www.w3.org/WAI/ARIA/apg/patterns/slider/)
- A web-component range slider documents firing `input` on pointer move and `change` on pointer up, the natural event pair to assert on for "live" vs "committed" values. — [range-slider-element](https://github.com/andreruffert/range-slider-element)
- Project test conventions: `cd horizon && npm run uat` (builds, 120+ checks) and `node e2e.mjs` (140+ checks), both blocking in CI and both run as a Plus customer and then free tier. — `/home/user/Retire-Lens-2/CLAUDE.md`

### Inferences
- Test plan for the instrument: (1) keyboard — focus face 2's range, press `ArrowRight` ×3, expect `aria-valuenow` +3 steps and the headline to change; `Home`/`End` hit min/max; `PageUp` moves the large step. (2) Pointer — `mouse.move` to a point on the ring, `down`, `move` through 10–20 interpolated steps around the centre, `up`; expect the backing value to change in the right direction, the headline to have updated *before* `up` (read it mid-drag), and after `up` the value to sit on a detent. (3) Flick — a fast short `move` sequence then `up`; expect the final value > the value at `up` (inertia ran) and still on a detent. (4) Alternative to drag — tap a detent mark or the +/− control and expect the same value change (WCAG 2.5.7 evidence). (5) Reduced motion — create the context with `reducedMotion: 'reduce'` and assert the dial still changes value and the headline updates with no intermediate frames (e.g. `getAnimations().length === 0` on the headline). (6) Worker — assert the confidence figure eventually matches a precomputed `runMonteCarlo` result for the same plan (seeded PRNG makes this deterministic) and that a rapid series of drags yields the result for the *last* plan only. (7) Screen reader surface — assert `aria-valuetext` strings are plain English with £ formatting and that the `aria-live` region's text changes once per gesture, not per frame.
- Because `hasTouch` tap only emits touchstart/touchend, the drum should listen to Pointer Events (not Touch Events) so the same mouse-driven test exercises the real code path on desktop Chromium and WebKit.

### Gaps
- Playwright's touchscreen cannot emulate a touch drag or multi-touch; real-device verification (BrowserStack or a physical iPhone/Android) is needed for iOS `pointercancel` behaviour and haptics.
- No source documents Playwright emitting `pointer*` events for `page.mouse` in WebKit specifically; it is standard behaviour but should be confirmed on the project's WebKit runner.
